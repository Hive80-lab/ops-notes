Your backups are lying to you: the 5-minute restore test most small teams skip

Last quarter a company told me their backups were "fine." Then a ransomware crew encrypted both the primary file server and the backup NAS that was mounted as a drive letter on the same server.

They had backups. They had never restored from them.

The uncomfortable truth: a backup you have never restored is a hope, not a capability.

The 5-minute restore test

Do this today, on any one system you care about:

  1. Pick one recent file or small folder (not the whole VM — start small).
  2. Restore it to a different location (/tmp/restore-test or a temp folder), never over the live copy.
  3. Open the file. Actually open it. Corrupt backups look fine in the console and fail on open.
  4. Write down how long it took. That number — not your retention policy — is your real recovery point.
  5. Set a recurring reminder. Monthly is fine. Weekly is better for anything critical.

If step 2 fails, you just paid five minutes to discover a data-loss incident in advance instead of during one. That is the cheapest incident you will ever have.

Two traps that quietly break restores

Trap 1: the backup account can see the production network. If your backup job runs as a domain admin from a machine that domain admins can log into, ransomware gets both copies in one move. Isolate the backup target at least one hop away.

Trap 2: nobody knows where the restore procedure lives. A restore runbook that only exists in one veteran's head leaves the company the day they do. Write it on one page. Store it somewhere reachable when your file server is the thing that's down.

What "good enough" looks like

  • One restore test per month, logged with date + time taken
  • Backup credentials that are not domain admin
  • A one-page restore runbook anyone on the team can follow
  • One offsite or immutable copy that production admins can't touch

None of this is exotic. All of it is the difference between "we have backups" and "we will be running again by lunch."
