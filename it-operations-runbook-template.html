What an IT Operations Runbook Actually Is

A runbook is a collection of procedures: what to do when things are normal, what to do when things break, and how to tell the difference. It's the difference between "only Sarah knows how to restart the database" and "anyone on the team can follow the runbook and restart the database correctly."

The goal isn't to document everything. The goal is to document the things that happen repeatedly and the things that happen at 2am — because those are the things that go wrong when nobody's thinking clearly.

The Six Sections Every Runbook Needs

Section 1: System Inventory

What exists, where it lives, and who owns it. One row per system.

  • ☐ System name
  • ☐ What it does (one sentence)
  • ☐ Where it's hosted (provider, region, URL)
  • ☐ Owner (primary + backup)
  • ☐ Dependencies (what else needs to be up for this to work?)
  • ☐ Monitoring: what alerts exist? who receives them?
  • ☐ Last reviewed date

Section 2: Daily Operations

The things that happen every day, every week, every month. If it's not written down, it's not happening consistently.

Daily

  • ☐ Check monitoring dashboard (what time, by whom)
  • ☐ Review overnight alerts (any that weren't auto-resolved?)
  • ☐ Verify backups completed (check the log, not the schedule)
  • ☐ Check disk space on critical systems
  • ☐ Review error logs for new patterns

Weekly

  • ☐ Apply security patches (schedule, test, deploy)
  • ☐ Review access logs for anomalies
  • ☐ Test one backup recovery (rotate through systems)
  • ☐ Update system inventory if anything changed

Monthly

  • ☐ Review and rotate API keys / credentials
  • ☐ Review vendor contracts and renewals
  • ☐ Run the 10-minute automation review
  • ☐ Update the runbook with anything that changed

Section 3: On-Call Procedures

What happens when someone gets paged at 2am. The runbook's most important section.

  • ☐ On-call schedule (who's on call this week? rotation?)
  • ☐ Alert routing: which alerts page the phone vs. go to email?
  • ☐ First response SLA: how fast should the on-call person acknowledge?
  • ☐ Escalation: when and how to escalate to the next person?
  • ☐ "Wake the boss" criteria: what warrants calling leadership at 3am?
  • ☐ Handoff: how does the on-call person pass unresolved issues to the next shift?

The shift handover log: A 10-minute sheet at the end of each shift — what happened, what's in progress, what the next shift needs to watch. This is the single most underrated ops document.

Section 4: Incident Response Procedures

For each common incident type, a numbered procedure. Not a essay — a checklist.

System Down

  1. ☐ Acknowledge the alert (stop the pager)
  2. ☐ Check the monitoring dashboard for scope (one system or multiple?)
  3. ☐ Post in the incident channel: "Investigating [system] down since [time]"
  4. ☐ Check recent changes (deploy log, config changes, vendor status page)
  5. ☐ Follow the system-specific recovery procedure (link to it)
  6. ☐ Verify recovery (run the smoke test)
  7. ☐ Post all-clear and update the incident log

Security Incident

  1. ☐ Isolate the affected system (do NOT power off — preserve evidence)
  2. ☐ Activate the incident response team
  3. ☐ Preserve logs (copy before they rotate)
  4. ☐ Assess scope: what data, what systems, what users?
  5. ☐ Contact legal/insurance if data breach is suspected
  6. ☐ Document everything (timeline, actions, decisions)

Section 5: System-Specific Procedures

One page per critical system. The format:

  • ☐ System name and description
  • ☐ How to check if it's healthy (the exact command or URL)
  • ☐ How to restart it (step by step, with the exact commands)
  • ☐ How to check logs (where are they, what to look for)
  • ☐ Common failure modes and fixes (the top 3)
  • ☐ How to roll back a deployment (the exact steps)
  • ☐ Vendor support contact (if managed service)
  • ☐ Dependencies: what else needs to be up?

Section 6: Contact Directory

Everyone and everything you might need to reach at 2am.

  • ☐ Team members (name, role, phone, email, timezone)
  • ☐ Vendor support (company, contract #, phone, hours, SLA)
  • ☐ Escalation contacts (management, legal, insurance)
  • ☐ Customer communication owners (who writes the status page?)

How to Start (When You Have Nothing)

If you're starting from zero, don't try to write the whole runbook at once. Start with the one thing that will save you the most pain:

  1. Write the system inventory first. 30 minutes. List every system, where it lives, who owns it. This alone prevents 50% of ops confusion.
  2. Pick the system that breaks most often. Write its recovery procedure. One page. Test it by having someone else follow it.
  3. Write the on-call schedule. Who's on call, how they're reached, when they escalate. Even if it's just two people.
  4. Add one procedure per week. The runbook grows organically. Don't try to write it all in one sitting.

The Runbook Anti-Patterns

  • ❌ The 200-page runbook. Nobody reads it. Keep each procedure to one page.
  • ❌ The runbook that's never tested. If someone else can't follow it and get the right result, it's not a runbook — it's a diary.
  • ❌ The runbook that's out of date. Systems change. If the runbook references servers you decommissioned 6 months ago, it's worse than no runbook.
  • ❌ The runbook only one person understands. If only the author can use it, the runbook has failed its purpose.

Common Questions

How long should a runbook be?

Each procedure should fit on one page. The total runbook length depends on how many systems you have, but if any single procedure exceeds one page, it's too complex. Break it down or simplify the system.

Should the runbook be in a wiki or a document?

Either works, as long as it's searchable and editable by the team. The key: it needs to be accessible during an outage. If your runbook is in the same system that's down, you have a problem. Keep an offline copy.

How often should I update the runbook?

Update it whenever something changes (new system, new procedure, team change). Review it monthly. Test one procedure per month by having someone who didn't write it follow it step by step.
