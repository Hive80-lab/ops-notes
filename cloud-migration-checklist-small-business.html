Cloud Migration Checklist for Small Business: Move Without Losing Data, Customers, or Weekends

The five-phase migration, the data integrity checks that catch silent corruption, the DNS cutover that doesn't lose email, and the rollback plan that saves your Saturday.

Cloud migration for small businesses fails the same way every time: the team treats it as a move (pick up, put down) instead of a migration (copy, verify, switch, verify again, then decommission). The data looks fine in the new system until someone opens a customer record and finds the email field truncated at 40 characters, or the date format flipped from DD/MM to MM/DD, or the related records that didn't migrate because the foreign key constraint was different. This checklist is for teams migrating their first major system to the cloud — email, file storage, CRM, or accounting.

Phase 1: Assess (week 1)

  • Inventory what you're moving. Not just "the file server" — how many files, how many shared folders, what permissions, what integrations (the accounting software that pulls from a shared folder, the scanner that emails to a distribution list). The software license register and service catalog capture the dependencies.
  • Identify the showstoppers. Legacy applications that can't run in the cloud. Compliance requirements that mandate on-prem storage. Bandwidth limitations (if your upload speed is 10 Mbps and you have 500 GB to migrate, that's 4.5 days of constant transfer). The single point of failure audit identifies what breaks if the migration goes wrong.
  • Estimate the real cost. Not just the subscription price — the migration labor, the parallel-run period (running both systems for 2-4 weeks), the training, and the "we didn't think of that" budget (plan 20% on top of the estimate). The annual ops budget template has the cost-comparison framework.

Phase 2: Plan (week 2)

  • Choose the migration window. A weekend when the system is least used. Not a holiday weekend (support is thin). Not month-end (if it's accounting). Check the seasonal peak calendar.
  • Write the rollback plan. If the migration fails at 11 PM Saturday, what's the plan? The old system needs to stay running in parallel until the cutover is verified. "We'll figure it out" at midnight is not a rollback plan. The change management checklist has the gate questions.
  • Notify everyone who will notice. Customers (if there's a downtime window), staff (who may need different login instructions Monday morning), and third parties who integrate with the system. Use the communication templates — a migration is a planned incident.
  • Pre-stage the data. Start the bulk data transfer during the week before the cutover. Most cloud providers support a pre-seed (initial sync) followed by a delta sync at cutover. This turns a 48-hour transfer into a 30-minute delta.

Phase 3: Migrate (the week of)

  • Run the bulk transfer. Monitor the transfer rate, error count, and any file-type exclusions. Large files, files with special characters in the name, and files over 15 GB (OneDrive's limit) need special handling.
  • Verify data integrity. Compare record counts, file counts, and total size between source and destination. Then spot-check 10 random records/files — open them, verify the content matches. Record counts can match while content is corrupted (encoding issues, truncation, date format flips). The post-deploy verification checklist has the full verification matrix.
  • Test access from outside the office. Cloud means anywhere-access, but it also means the old "it works because you're on the LAN" assumptions are gone. Test from a phone, from home, from a coffee shop. If it doesn't work from outside, you've migrated to a system that's less accessible than the one you left.

Phase 4: Cutover (the weekend)

  1. Final delta sync. Copy only what changed since the bulk transfer. This should be minutes, not hours.
  2. Switch DNS. If migrating email or web, update DNS records with the low TTL you set in phase 2. Plan for DNS propagation (up to 48 hours globally, though usually 1-4 hours). The SSL certificate runbook covers the cert side of the cutover.
  3. Verify in the new system. Log in as a real user (not admin). Create a test record. Edit it. Delete it. Send a test email. Upload a file. If any of these fail, consult the rollback plan.
  4. Keep the old system running. Do not decommission the source for at least 2 weeks. You will need it — either for rollback or for the "we forgot to migrate that folder" discovery.

Phase 5: Verify (the 2 weeks after)

  • Daily check for the first week: are users able to work? Are there support tickets that trace to the migration? Is the old system still needed (check before decommissioning)?
  • Decommission the old system. Only after 2 weeks of clean operation. Back it up first — the backup strategy checklist applies to the decommissioned system too. Update the service catalog to reflect the new system.
  • Run the after-action review. What went well, what didn't, what would you do differently. The after-action report template captures this for the next migration.

Worked example: the 20-person marketing agency

A 20-person marketing agency migrated from an on-prem file server to SharePoint Online. They pre-staged 800 GB during the week (took 3 days at 25 Mbps), ran the delta sync on Saturday morning (12 minutes), cut over DNS at 10 AM, and verified by 11 AM. Monday morning, three issues surfaced: (1) a shared scanner couldn't email to the new SharePoint library (needed a different email address format), (2) two freelancers couldn't access external-shared folders (permission model was different from NTFS), and (3) the accounting integration that pulled from a shared folder broke (the folder path changed). All three were fixable within the day because the old server was still running. The agency kept the old server for two weeks, fixed the scanner on Monday, re-shared the folders on Tuesday, and updated the accounting integration on Wednesday. Decommissioned the old server on day 15. Total migration cost: the SharePoint licenses, 8 hours of IT contractor time, and one Saturday morning. The key: they pre-staged, they kept the old system running, and they didn't decommission until everything worked.
